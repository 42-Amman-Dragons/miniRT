miniRT geometry note

Why the sphere normal needs no matrix

The old implementation created an identity matrix, inverted it, transposed it, multiplied tuples by it, and freed several allocations for every visible pixel. In this project, all of that work returns the same direction as one subtraction. The book uses those operations for a valid reason—but it uses a different way of representing shapes.

Short answer: the sphere is already stored in world space as a center and radius. At surface point P, its outward normal is simply normalize(P - center).
Current representation

What the sphere knows

typedef struct s_sphere
{
    t_tuple     center;
    double      radius;
    t_material  material;
} t_sphere;

The center is already the sphere's final location in the scene. The radius is already its final size. There is no object-to-world matrix stored here, so there is no transform to undo.

The geometry

A sphere contains all points whose distance from its center C equals its radius r:

|P - C|² = r²

The vector P - C starts at the center and points through the surface. It is perpendicular to the sphere at P, which is exactly what a surface normal means. Its length is the radius, so we normalize it to length one:

N = normalize(P - C)

Another derivation uses the gradient of F(P) = |P - C|² - r². Its gradient is 2(P - C). Normalization removes the factor of two, giving the same result. The radius does not appear in the final code because normalization also removes the vector's original length.

Old work versus necessary work

Identity-matrix path

Create I→Invert I→ Transform P→Subtract C→ Transpose I→Transform N→ Normalize

Because the matrix is the identity, I⁻¹ = I and I⁻ᵀ = I. Multiplication by it changes nothing. Every allocation, inversion, transpose, and free is therefore overhead.

Direct world-space path

Subtract C from P→Normalize 
t_tuple normal_at(t_sphere sphere, t_tuple point)
{
    return (normalize_vector(
        sub_tuples(point, sphere.center)));
}

A numerical example

Let the center be C = (1, 2, 3) and a surface point be P = (1, 5, 7). Then:

P - C = (0, 3, 4)
|P - C| = 5
N = (0, 3/5, 4/5) = (0, 0.6, 0.8)

The radius happens to be five, but it is not needed explicitly. The length of P - C already contains that information, and normalization removes it.

The book's design

Why The Ray Tracer Challenge needs matrices

In the book, every sphere begins as one canonical object: a unit sphere centered at the object-space origin. Its equation is always x² + y² + z² = 1. A transformation matrix M then tells the renderer how that canonical sphere appears in the world.

Object space

center = (0, 0, 0)
radius = 1

// Always the same simple sphere

Intersection and normal formulas stay simple because every shape is solved in its own local coordinate system.

World space

M = translation * rotation * scaling

// M can move the sphere,
// resize it, or turn it into an ellipsoid

One matrix can describe combinations that a single center and radius cannot, especially non-uniform scaling and shearing.

The book's complete coordinate-space journey

World ray→ M⁻¹ →Object ray →Unit-sphere intersection→ Object point→Object normal → M⁻ᵀ →World normal

1. Intersect in object space

The incoming ray is expressed in world coordinates. Multiplying it by M⁻¹ reverses the sphere's transformation and moves the ray into the canonical sphere's coordinate system. 

object_ray = transform(world_ray, inverse(M));
intersections = intersect_unit_sphere(object_ray);

2. Return the normal to world space

The hit point goes into object space, where the unit-sphere normal is simply object_point - origin. That normal must then return to world space using the inverse transpose. 

object_point  = inverse(M) * world_point;
object_normal = object_point - origin;
world_normal  = transpose(inverse(M)) * object_normal;
world_normal.w = 0;
return normalize(world_normal);

Why not transform the normal with M?

A surface normal must remain perpendicular to every tangent on the surface. If an object-space tangent is T, its world-space version is MT. We need a transformed normal that still has a zero dot product with that tangent.

Nworld = M⁻ᵀ N
Nworld · Tworld = (M⁻ᵀN) · (MT) = N · T = 0

That is why the transpose is not decorative. With non-uniform scaling, using M directly can tilt the normal away from the true perpendicular direction and produce visibly incorrect lighting.

Book sphere versus this miniRT sphere

Question Book model Current miniRT model
Where is the sphere? Encoded in transformation matrix M Stored directly in sphere.center
How large is it? Encoded in M's scaling Stored directly in sphere.radius
Can it become an ellipsoid? Yes, through non-uniform scaling No; one radius always describes a round sphere
Normal calculation Object normal, then inverse transpose normalize(point - center)
The book's matrix code is correct for the book's representation. It became unnecessary here only because this project changed the data model from “unit sphere plus transform” to “world-space center plus radius.”

When matrices really are needed

Sphere design Normal calculation Reason
World-space center + radius normalize(P - C) The final position and uniform size are already stored.
Unit sphere + translation matrix Matrix method is possible but unnecessary Translation can be represented directly by changing C.
Unit sphere + non-uniform scaling Use the inverse transpose The result is an ellipsoid; direct center/radius is no longer enough.
General transformed object Nworld = transpose(inverse(M)) × Nobject Normals must stay perpendicular after scaling and shearing.

Why the inverse transpose exists

A normal is not an ordinary direction vector. Under non-uniform scaling, multiplying it by the object's matrix can make it no longer perpendicular to the surface. Multiplying by the inverse transpose preserves that perpendicular relationship.

That rule is important for transformed ellipsoids and general meshes, but it does not apply to this t_sphere: the structure has no transformation matrix and represents only a round sphere with one uniform radius.

Why the old version was slow

Ray tracing calls normal_at() once for every visible hit. At 800 × 600, hundreds of thousands of pixels may hit a large sphere. The old function performed matrix allocations and a full inversion for each one. The direct version uses one subtraction, one magnitude, and one division—without heap allocation.

Even in the book's transformed-object design, a production renderer should avoid rebuilding and reinverting an unchanged matrix at every pixel. The transform or its inverse can be stored with the object and reused across rays.

Rule to remember: choose the normal calculation that matches how the object is stored. World-space center/radius sphere: subtract and normalize. Transformed object-space geometry: transform the point to object space and return the normal with the inverse transpose.
